## 4. Integrate one shared diagnostic workflow

Create a reusable diagnostic service/tool layer and a compact shared workflow contract.

Integrate it through the existing coordinator and relevant existing skills. Do not copy a large debugging prompt into every skill.

Activate the shared path for:
- Explicit debugging questions.
- Invalid YAML or configuration.
- Missing or ambiguous hooks.
- Compilation and API/version mismatches.
- Failed or unexpected test executions.
- Assertion failures or errors.
- Missing results.
- Timeouts.
- Contradictory documentation, package, or runtime evidence.

Carry the current task, evidence, and established project facts into diagnosis. Do not require a separate debug command or repeat onboarding unnecessarily.

Do not trigger expensive diagnostic inspection for ordinary successful tasks.

Shared procedure:
1. Establish the exact project, execution, package set, and available capabilities.
2. Collect existing evidence before requesting another execution.
3. Identify the first relevant observed failure and its exception chain.
4. Compare intended configuration with available runtime configuration evidence.
5. Inspect matching installed API contracts, implementation, and local documentation.
6. Separate observed facts from hypotheses.
7. Identify plausible alternative explanations.
8. Choose the smallest check that distinguishes those explanations.
9. Use authorized fresh evidence to confirm or reject the hypothesis.
10. Return the diagnosis and bounded repair scope to the originating skill.

Classify causes as:
- Test logic.
- Configuration.
- Custom hook.
- QaaS framework.
- Tested system.
- Environment/deployment.
- Tooling/dependencies.
- Unknown.

A QaaS stack frame does not prove a framework defect. A failed assertion does not prove the assertion is wrong. A zero process exit does not prove the intended test outcome.

## 7. Use the installed QaaS diagnostic capabilities

Verify these capabilities against local packages, help, documentation, and
sample output before relying on them.

Framework capabilities:
- LoggerOptions.JsonLogs corresponds to --json-logs.
- The flag formats default console events as newline-delimited Serilog JSON.
- Explicit --logger-configuration-file configuration takes precedence.
- Text logging remains the default.
- JSON events can contain Timestamp, Level, MessageTemplate, RenderedMessage,
  Properties, and Exception.
- Exception may be formatted text rather than a structured exception object.
- --json-logs does not enable network logging.
- --disable-elastic-defaults disables registered Elastic defaults; explicitly
  enabling --send-logs can still enable shipping.
- Logging flags do not disable network operations performed by tests.
- SDK packages can include XML API documentation.
- Assemblies can contain embedded portable PDBs and original source.

Runner capabilities:
- Event ID 4102, ConfigurationRejected, Warning:
  configuration rejection during a runner lifecycle phase.
- Event ID 4101, PhaseFailed, Error:
  another exception during a runner lifecycle phase.
- Lifecycle events include Phase and exception evidence.
- Phase values are human-readable text; do not assume enum identifiers.
- The normal Microsoft-to-Serilog bridge represents EventId under Properties,
  commonly with Id and Name fields.
- Assertion completion is a Debug event with:
  DiagnosticCode = QAAS_ASSERTION_COMPLETED
  AssertionName
  AssertionType
  AssertionStatus
- AssertionStatus is a named status, not a process exit code.
- YAML parser/load wrappers preserve original inner exceptions.
- Friendly outer configuration exceptions may intentionally hide their stack.

These events do not necessarily cover every bootstrap or configuration failure.
Missing Debug events do not prove an assertion never executed.

Support older packages and custom formatters through text-log/report fallbacks.

not proof of causation.

expanded configuration, raw payloads, or entire reports.

- Repair scope, if established.
